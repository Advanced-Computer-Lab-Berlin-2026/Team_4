# Sprint 2 integration contract

The Member 1 HTTP endpoints and test commands are in [Member 1](sprint2/member1.md). Use feature-specific backend route files and a default export of route entries in `client/src/routes/sprint2/memberN.routes.jsx`. React pages remain lazy and route declarations are discovered by the shared configuration. Keep paths unique. Run client Sprint 2 tests in `client/test/sprint2/*.test.jsx` with `npm run test:sprint2 --prefix client`.

| Owner | API and ownership |
| --- | --- |
| 1 | `availability.getAvailability(itemId, range, options?)` and `checkOverlap(itemId, range, excludeReservationId?, options?)` accept UTC date ranges and optional `session`. They include unexpired holds and pending, confirmed and active reservations. |
| 1 / 3 / 5 | Use `reservationCommands.transition` and `extend` as described below. Call the command from the owning feature's controller and use its returned document. |
| 1 / 3 / 6 | `reservationCommands.withReservation({actorId,reservationId,session?}, callback)` passes the reservation, authenticated actor and session inside the item/borrower lock. A feature callback checks action-specific roles/state and saves only the fields it owns. |
| 1 / 7 | `holdForWaitlist({borrowerId,itemId,startDate,endDate,expiresAt,session?})` claims availability atomically. Pass the resulting hold ID as `holdId` on single-item checkout, with the matching borrower, item and dates. `releaseWaitlistHold({holdId,itemId,borrowerId,session?})` releases a claim. M7 owns queue eligibility, priority and expiry policy. |
| 5 | Checkout validates the full cart and removes only entries that still match the checked-out ID, item and dates. A future borrow-list service hand-off must keep stale entries visible to checkout and compare the saved line snapshot before clearing it. Borrow-list mutations should be field-scoped or use optimistic concurrency. Link the borrow-list page to `/checkout`. |
| 7 | Link item details to `/reserve/:itemId`, or link a waitlist offer directly to `/checkout?source=single&itemId=…&startDate=…&endDate=…&holdId=…`. |

Every writer of reservation status or dates uses the command layer. MongoDB handles lock contention within the transaction. In code with an existing session, call the command before any operation with a dependency on availability and acquire locks in stable order. Quote and availability reads are advisory until the transaction rechecks them. If a transaction can be retried, transactional mutations belong inside the callback and external side effects belong after commit.

## Member 3 and Member 5 lifecycle

The shared reservation engine uses UTC date-only fields. A reservation blocks the half-open interval `[startDate, endDate)`. A booking from December 1 to December 3 lasts two days and is due at `December 3 00:00 UTC`. Inventory can be booked again starting December 3. Returns at or before the deadline are on time. Use `returnTiming.isLateReturn(returnedAt, endDate)` for trust and late-fee decisions.

- Use `transition({ actorId, reservationId, action, expectedStatus?, reason?, session?, beforeCommit? })` with `confirm`, `reject`, `pickup`, `return` or `returnDamaged`. The actor must be the verified lender of that reservation. Use `confirm` for the UI's **Approve** action. `reject` accepts a reason up to 500 characters and refunds the held deposit and any charged delivery fee in full through Member 2. Pickup is allowed within the booked interval.
- For a good return, call `return` once. The command refuses damage cases, stamps `returnedAt` and `completedAt`, releases the deposit, applies any late fee, invokes trust for both participants and enqueues completion and availability events when the providers are present. Payment, trust and event providers receive the booking transaction. Client or controller code should use the command without repeating those side effects.
- For a damaged return, Member 5 opens Member 3's damage form while the reservation is active. Member 3's report endpoint calls `returnDamaged` with `beforeCommit(reservation, session)` and inserts the open `DamageReport` in that session. The callback can read the completed reservation with `returnedAt` in the same transaction. The command leaves the deposit held and still handles late fees, trust and completion events. A zero-deposit reservation may have a damage case with zero forfeiture. Failure to insert the case rolls back the return. On a retry, fetch the existing report by reservation ID.
- `DamageReport` is the source of truth for an existing or open case. The shared engine checks it inside the booking transaction. Member 3 can expose `hasOpenDamageCase` for Member 5's UI and should coordinate evidence mutations through the same reservation lock. Legacy completed records can use `completedAt ?? returnedAt` for the review window.
- Condition-photo metadata is `{ _id, path, takenAt, uploadedBy, originalName, mimeType, size }`. Mount `uploadConditionPhotos` after the lender/participant checks. Send multipart fields named `photos`, up to five JPEG or PNG uploads per request, each under `MAX_UPLOAD_MB`. Use `fileInfo` to build the stored metadata and keep `path` server-side. Member 3 owns the total-per-stage cap, stage authorization, evidence locking, authorized streaming and orphan cleanup if a transaction fails.
- Member 3 may update `User.trustScore` and `User.stats.*` using field-level updates. `reviews/trust.js` exports `recalculateTrust(userId, { eventKey, session })` and should use the supplied session for reads and writes. Full-history recalculation needs no separate event-deduplication model. Use `completed` for notification delivery. It represents the recorded return and completion, with `returnedAt`, `completedAt` and `returnCondition` in the payload.
- Use `extend({ actorId, reservationId, action, endDate?, requestId?, session? })`. The borrower can `request` or `cancel`. The lender can `approve` or `reject`. A new request has an `extension.requestId`, which the UI must send when acting on it. Pending requests expire at the original due time and are displayed as `expired`. Only approval changes the due date and it rechecks the overlap atomically.
- Use `returnTiming.lifecycleFlags(reservation)` for overdue approval, missed pickup, overdue return and effective extension status. These are derived flags. Reservations retain their stored state unless a lifecycle action succeeds. A lender can reject an unanswered pending request. Confirmed missed pickups and overdue returns have no automatic cancellation, refund or completion policy. Overdue active reservations can still be returned, triggering Member 2's late-fee policy. This is separate from automatic expiry of temporary payment/waitlist holds.

## Member 2 payment module

Export the following from `server/src/services/payments/payment.js`.

- `chargeWalletCheckout(input, session)` atomically debits the total and writes ledger/audit rows for the supplied reservation IDs. Throw a validation or conflict error on insufficient funds. Return only once the mutations in the supplied transaction have succeeded.
- `releaseDeposit({ userId, reservationId, reference, amountMinor, currency, idempotencyKey }, session)` credits the held deposit on a good return. A lender rejection reuses `refundToWallet` with the same fields and the full paid amount. The call includes `depositMinor` and `deliveryMinor` for ledger allocation. These methods update wallet, ledger and audit in the supplied session. The reservation command owns the deposit status.
- `applyLateFee({ userId, reservationId, reference, returnedAt, endDate, currency, idempotencyKey }, session)` applies the late-fee policy in the supplied session and returns `{ feeMinor }`. It runs only for an overdue return. A paid transition requires the appropriate provider to succeed.
- `settleCancellation(input, session)` credits the borrower's wallet and records the refund in the same transaction. The input includes `reservationId, borrowerId, amountMinor, deliveryMinor, currency, cancelledAt, pickupDate, freeCancellationHours, idempotencyKey`. `amountMinor` is the held deposit, which may be zero for a delivery-only charge. For eligible cancellation before handover and the pickup deadline, refund the full delivery fee independently of the deposit. Return `{refundMinor, deliveryRefundMinor}` in minor units. The deposit's forfeiture is based on `refundMinor` alone. The command rolls back when a charged delivery fee is missing from the settlement.
- `startCardPayment(input)` starts or resumes a Stripe-hosted payment using the supplied idempotency key. Return `{state:"pending",redirectUrl}` for an active session. Use `/checkout/status/:attemptId` as the application's return path.
- `getCardPayment(input)` reads authoritative provider state. Return `{state:"pending",redirectUrl?}`, `{state:"failed"}` for definitive nonpayment, or `{state:"paid",reference,amountMinor,currency}`. When `closeExpired` is true, close further attempts definitively before returning failed. Handle late success and provider creation retries using the durable payment operation. A still-unknown result remains pending.
- `recordCardCheckout(input, session)` persists the ledger/audit records for a verified card payment before reservations commit. The input includes `paymentReference` and the reserved line IDs.
- `verifyCheckoutWebhook(rawBody, signature)` verifies a Stripe event and returns an affected checkout attempt ID, or `null` for unrelated events. Use the mounted raw-body route at `/api/stripe-webhook` as the single callback.
- `refundFailedCheckout(input)` compensates the verified provider payment identified by `paymentReference`, including any provider amount mismatch. This operation is retried using the same checkout reference and must be idempotent across instances.

Checkout payment input includes `attemptId, borrowerId, idempotencyKey, amountMinor, currency, expiresAt, lines`. Each line includes the planned `reservationId`. Wallet and cancellation mutations use the caller's MongoDB session. Stripe calls occur outside database transactions. Keep a durable Stripe operation and idempotency keys for initialization, compensation and callback processing. The server reconciles expired attempts and pending compensation in the background.

## Pricing, membership and events

- M6 exposes `validateBooking(actor,item,range,entitlements,{session})` from `policies/bookingPolicy.js` and `quote(item,range,entitlements,promo,fulfilment,{session,borrowerId})` from `pricing/depositQuote.js`. A quote contains `{amountMinor,deposit:{base,categoryMultiplier,tierDiscountPercent,promoDiscount,amount},fulfilment:{method,deliveryFee,deliveryAddress?},promoCode?}`. Deposit and fee fields use EGP. If a code is used, `promotions/promo.js` exposes `redeemCheckoutPromo({promoCodeId,reservationId,borrowerId},session)`, which atomically validates and records redemption. Delivery/promo UI components can call the existing checkout selection contract when their owner is ready.
- M8's route and service details are in [Member 8's membership contract](sprint2/member8.md) once that branch merges. The member and admin menu entries activate when `/membership` and `/admin/membership-report` are registered. M8 exposes `getEntitlements(userId,at,session)` from `membership/entitlements.js`, returning `{discountPercent,maxConcurrentReservations, ...}`. M1 serializes the capacity check across items for each borrower. The baseline uses the stored individual tier and accepts ordinary pickup. Household quotes and delivery/promo selection require their owning integrations.
- Membership payments still require M2 to expose `chargeMembership` and `recordMembershipPayment` for M8's subscribe, pay and cancel flows. Both members should use M8's contract for the exact inputs. For hosted card payments, support a server-selected membership return path such as `/membership`. Reservation checkout keeps its own status page.
- M6 applies `discountPercent` to deposit pricing, M7 consumes `waitlistPriority` for queue ordering, and M9's membership change and renewal notifications should link to `/membership`.
- M9 exposes `enqueueEvent(type,aggregateId,recipients,payload,eventKey,session)` from `notifications/eventOutbox.js`. Use the supplied session and deduplicate by event key. Events include `confirmed`, `cancelled`, `rejected`, `picked_up`, `completed` and `availability_changed`. Payload includes `reservationId,itemId,borrowerId,status,startDate,endDate`. The worker processes referral eligibility on `completed`. Optional startup functions are `startNotificationWorker()` and `startReminders()` in `server/src/jobs/notificationWorker.js` and `server/src/jobs/reminders.js`. Production email delivery and reminder scheduling belong to Member 9.

## Member 6 checkout and delivery handoff

- The shared checkout page uses M6's fulfilment and promo components. For a single checkout, send `fulfilment: {method, deliveryAddress?}`. For a borrow list, send `fulfilmentByEntry: { [entryId]: {method, deliveryAddress?} }` with IDs from the server's quote lines. Omitted entries use pickup. Use the same selection and `promoCode` for quote and submit. Address, promo and fulfilment changes require a fresh quote. The server determines eligibility and fees. A legacy whole-cart `fulfilment` remains accepted when no per-entry map is sent.
- Each reservation whose deposit is reduced consumes one redemption. A cart exceeding the remaining count or a one-per-member code's allowance is rejected during pricing. Redemptions are rechecked and recorded in the booking transaction. Card attempts that have already been paid use the existing compensation path if they can no longer redeem the code.
- M6's delivery endpoint calls M1's `advanceDelivery({actorId,reservationId,deliveryStatus})`. The owning verified lender dispatches a confirmed booking and marks it delivered within the booked dates. The final stage activates it and stamps `pickedUpAt` in the same transaction. Use the ordinary `pickup` action only for pickup orders. M9 receives one `delivery_status` event per successful stage with the tracking link and no address.
- The participant reservation endpoint includes `fulfilmentMethod`, `deliveryStatus` and `deliveryFee`. Read the address from the participant-only `GET /api/delivery/reservations/:id`. The shared `/my-reservations/:reservationId` page keeps chat and cancellation and embeds `DeliveryStatusPanel` for deliveries.
- M5's `/reservations` and `/reservations/:id` paths are distinct from M1's `/my-reservations`. Shared navigation and checkout use M5's paths when registered. M5 embeds M6's panel for delivery, keeps its pickup button for pickup, refreshes its detail response on `onChange`, and links to M1's chat/cancellation. Delivery settings are already mounted in the saved listing's M6-owned Pickup & rules tab. M5 should keep that tab mounted in the editor.

## Member 5 borrow list and listing archive

- The shared reserve page mounts Member 5's `BorrowListButton`. Navigation shows the borrow list and lender dashboard when their routes are registered. Member 7 can also embed the button on catalog details.
- Archiving checks open bookings and unexpired holds under the shared booking lock. Older drafts without valid dates stay visible and can be edited or removed.
- Reservation details show Member 3's optional review form for completed bookings and mount the condition-photo panel on confirmed, active and completed bookings when the component exists. The API controls the lender's upload windows and borrowers see the evidence read-only.

## Member 4 moderation, analytics and support

Member 4's route declarations use the existing default-exported `{ path, access, element: Component }` contract. Shared navigation displays Member 4's links when the routes are registered. For moderation, `User.isFlagged` is a review marker independent of the existing account status. Use field-scoped writes and protect administrator accounts. Listings already use `Item.moderationStatus`. Usage reports count reservations by UTC start date, and damage reports read the existing reservation and damage schemas. When Member 3's decision page is available, report rows can link to `/admin/damage-reports/:id`.
